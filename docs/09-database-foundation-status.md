## Database Architecture

The database layer follows exactly one rule throughout: **`app/db/` is the only package in the entire application permitted to construct a database engine, open a session, or hold SQLAlchemy connection logic** (`docs/04-backend-architecture.md`, Section 1). Nothing in this prompt weakens that boundary — it's now enforced by real, working code instead of only a placeholder docstring.

```
app/db/base.py            → shared declarative Base + constraint naming convention
app/db/model_registry.py    → the single import point for future domain models
app/db/session.py             → engine + session factory + get_db() FastAPI dependency
app/db/errors.py                → translates SQLAlchemy exceptions → shared AppError vocabulary
app/db/testing.py                 → isolated in-memory test database strategy
alembic.ini / alembic/env.py        → migration tooling, wired to Settings + Base.metadata
```

**Connection flow (once a future route needs it):**

```
router.py  --Depends(get_db)-->  app/db/session.py:get_db()
                                        |
                                        v
                        get_session_factory() (cached)
                                        |
                                        v
                             get_engine() (cached, lazy)
                                        |
                                        v
                          Settings.database_url (app/core/config.py)
```

The engine is **lazily created on first use**, not at application startup — this was a deliberate decision (see below) so the application can still boot cleanly in an environment where `DATABASE_URL` isn't yet configured, since nothing in the current codebase actually needs a database connection yet (no domain model, no route depends on `get_db()`).

**Error flow:** any exception raised while a session is open is caught in `get_db()`'s `except` block, translated via `app/db/errors.py::translate_db_exception()` into a `DatabaseUnavailableError`, `ConflictError`, or `TransactionError` (all subclasses of Prompt 8's `AppError`), and re-raised — meaning it flows straight into the *already-existing* global handler from `app/core/error_handlers.py` with zero new wiring required there.

## Future Model Integration Approach

Recorded explicitly so the next domain-implementation prompt has a clear, minimal checklist rather than needing to reverse-engineer the pattern:

1. Implement `app/domains/<name>/models.py`, with model classes inheriting from `app.db.base.Base` — faithfully implementing the corresponding entity/entities from `docs/03-data-architecture.md`.
2. Add exactly one import line to `app/db/model_registry.py::register_all_models()` for that domain's models module.
3. Run `alembic revision --autogenerate -m "add <domain> tables"`, review the generated migration, then `alembic upgrade head`.
4. Implement `app/domains/<name>/repository.py`, using `Depends(get_db)` (or a session passed into it by the Service Layer) — this is the *only* file in that domain permitted to write SQLAlchemy queries, per Prompt 4/8's layering.
5. If that domain needs dedicated test coverage, use `app/db/testing.py::test_session()` as the fixture foundation — no new test-isolation mechanism should be invented per domain.

No domain currently does any of this — it's written here as the contract the *next* prompt will follow, not as something already executed.

## Migration Philosophy (reaffirmed, see `alembic/README.md` for full detail)

- Every schema change is an explicit, incremental, reviewed migration — never a manual database edit, in any environment.
- Migrations are additive by default; destructive changes are deliberate, separate steps.
- **Migration failures are treated as operational (CLI/deploy-time) concerns, not request-time errors** — `app/db/errors.py` deliberately does not attempt to catch or translate a failed `alembic upgrade`; a partially-applied schema should stop a deploy, not be silently worked around by a running application.
- The connection string is read from exactly one source (`Settings.database_url`, i.e. the environment) by both the running application and Alembic — there is no second place it can be configured and drift out of sync.
